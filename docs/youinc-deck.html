Multi-Tenant Isolation

Every row carries a tenant_id.

⛨

Row-Level Security

RLS enforced on every business table — raw_transactions, journal_entries, manual_account_balances, classification_rules.

ƒ

SECURITY DEFINER helpers

user_tenant_ids() and is_tenant_member() check membership before any access.

✗

WITH CHECK guards

Prevents an INSERT/UPDATE from moving a row into another tenant's ownership.

✓

Tested boundaries

Server-side guarantee: every server function calls requireTenant() and uses a request-scoped Supabase client under the user's RLS context — never service_role.

Security & Auth

Defense in depth.

✓

Two independent auth systems. Passkey/WebAuthn for the private dashboard; Supabase Auth for self-service multi-tenant.

✓

Session gate. Passkey session required only for /dashboard; everything else public by default.

✓

Independent checks. Every server function calls requireSession() / getServerUser() — no shared trust assumption.

✓

Short-lived credentials. Passkey challenges/sessions expire on 5-minute / 30-day TTLs.

✓

Vault-encrypted secrets. Akahu tokens encrypted via connect_akahu RPC; app token server-only.

✓

Request-scoped RLS. Supabase server client built from request cookies per the @supabase/ssr pattern, plus default CSRF middleware.
